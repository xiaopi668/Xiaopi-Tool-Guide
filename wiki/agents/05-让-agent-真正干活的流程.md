# 让 agent 真正干活的流程

> 给目标、先计划、小步改、认真验收

`AI 编程助手` · 建议 14 分钟 · 进阶

## 学完这一节，你会

- 写出 agent 能执行的任务描述
- 用「先计划后动手」减少返工
- 建立一套可重复的验收习惯

## 开场三件套

一条好的任务描述包含三样东西：**目标**（要什么结果）、**约束**（不能碰什么、用什么方案）、**验收**（怎么算完成）。缺哪一样，agent 就会自己猜，猜错就要重来。

## 同一件事，两种说法

| 模糊指令 | 可执行指令 |
| --- | --- |
| 帮我优化一下这个页面 | 首页首屏 LCP 超过 2.5s，找出前三个原因并给方案，先不要改代码 |
| 把测试修好 | pnpm test 有 3 个失败，修到全绿，不要改测试断言 |
| 重构用户模块 | 把 src/user 里的请求逻辑抽到 api.ts，行为不变，补单测 |
| 看看有没有问题 | 检查 src/pay 的错误处理，按严重程度列问题，先不要改 |

> 差别不在字数，而在**能不能验证**。能验证的要求，agent 才知道什么时候该停。

## 一次任务的完整流程

### 1. 先读

让它读相关文件并复述现状，确认它理解的和你想的一致。

### 2. 给计划

要求列出改动文件、步骤、风险，先不要写代码。

### 3. 小步执行

一次只做一步，做完跑测试，绿了再继续。

### 4. 验收

看 diff、跑测试、手动点一遍关键路径。

### 5. 提交

按改动拆成多条提交，信息写清做了什么、为什么。

## 先计划，后动手

计划阶段是成本最低的纠错点。一句「先给方案，我确认后再改」能挡掉大部分方向性错误。计划里重点看三件事：**要改哪些文件**、**有没有漏掉的调用方**、**怎么验证**。

## 小步提交的价值

让 agent 一次改二十个文件，出问题时你无法判断是哪一步坏的。改成一次一个文件、一次一个行为，每步跑一次测试，出问题能立刻定位，也能单独回滚。

> **提示：报错要贴完整**
>
> 「不行」「还是报错」会让它开始瞎猜。把**完整错误、执行的命令、期望结果**一起给它，定位速度会快一个数量级。

## 上下文是要管理的

会话越长，早期信息越容易被挤出窗口。做法：任务切换就新开会话；阶段性结论写进 `CLAUDE.md` / `AGENTS.md`；长任务用 `/compact` 压缩而不是硬撑。还有一个便宜的办法：让它每完成一步就用一句话总结当前状态。你复制这条总结到新会话，比拖着旧上下文更清楚。

> **注意：不要盲信「已完成」**
>
> agent 说完成，只代表它认为改完了。测试没跑、diff 没看、边界没测，就不算完成。把「跑测试 + 看 diff」当成固定动作，而不是可选项。

## 常见失败与对策

| 症状 | 常见原因 | 对策 |
| --- | --- | --- |
| 改错文件 | 没先读结构 | 先让它复述目录与入口 |
| 越改越乱 | 一次改太多 | 拆成小步，每步验证 |
| 反复修不好 | 缺少报错上下文 | 贴完整错误与命令 |
| 测试被改绿 | 只求通过 | 明确「不要改测试断言」 |
| 上下文丢失 | 会话太长 | 新开会话或压缩 |

## 任务模板（可直接套用）

```text
目标：修复「导出 CSV 时中文乱码」。
现状：src/export/csv.ts 用默认编码写出，Windows Excel 打开乱码。
约束：只改这个文件与对应测试，不要升级依赖。
验收：新增单测覆盖 BOM 场景，pnpm test --run 全绿。
先给计划，我确认后再改。
```

> **提示：一次只问一件事**
>
> `把「顺便再改个样式」塞进同一个任务，会让 diff 变脏、回滚变难。一次只做一件事，做完验收、提交，再开下一个。`

## 动手练一练

把一件真实的小任务，按「目标 / 约束 / 验收」写成一段指令交给 agent。

1. 写清目标、约束、验收标准
2. 要求它先给计划，不要动代码
3. 确认计划后分步执行
4. 跑测试并 review diff

**完成标准**：全程只返工一次以内，且每条改动都能对应到计划里的一步。

## 小测验

<details>
<summary>展开题目与答案（3 题）</summary>

**1. 一条可执行的 agent 指令，最少要包含什么？**

- A. 目标和验收标准
- B. 越详细越好，没有重点
- C. 只要一句「帮我改」
- D. 模型名称

<details><summary>答案</summary>

**A**。目标决定做什么，验收决定何时停。约束用来防止它跑偏。

</details>

**2. 为什么要先让它给计划？**

- A. 显得专业
- B. 计划阶段纠错成本最低
- C. 能减少 token
- D. 必须走流程

<details><summary>答案</summary>

**B**。方向错了，越早发现越省事。计划里能看出它要改哪些文件、怎么验证。

</details>

**3. 测试失败时，怎样描述最有效？**

- A. 说「还是不行」
- B. 贴完整报错、命令和期望结果
- C. 让它自己猜
- D. 把测试删掉

<details><summary>答案</summary>

**B**。完整错误 + 命令 + 期望，能直接定位；模糊描述只会让它反复试错。

</details>

</details>
