# 权限、沙箱与安全

> 给 agent 多大权限，才既好用又不出事

`AI 编程助手` · 建议 12 分钟 · 进阶

## 学完这一节，你会

- 知道 agent 能造成的真实风险
- 按任务选择权限与沙箱范围
- 建立上线前的检查清单

## 它能执行命令，就能造成后果

agent 的工具箱里有终端。能跑 `npm test`，就能跑 `rm -rf`、`git reset --hard`、`curl | sh`。风险不是「模型有恶意」，而是**它在错误的理解下执行了正确的命令**。

## 风险与对策

| 风险 | 典型场景 | 对策 |
| --- | --- | --- |
| 误删文件 | 清理临时文件时路径写错 | 工作区沙箱 + 提交后再操作 |
| 覆盖未提交改动 | reset --hard、checkout | 先 commit 或 stash |
| 泄露密钥 | 把 .env 贴进对话或提交 | .gitignore + 不粘贴密钥 |
| 执行恶意脚本 | curl 陌生脚本直接跑 | 先读脚本再执行 |
| 供应链风险 | 安装来源不明的包 | 锁定版本、审查依赖 |

## 最小权限

默认停留在**工作区写入**。需要装系统包、改全局配置、访问工作区外的路径时，再临时放宽，用完收回。这不是麻烦，而是把「一次误操作」限制在可恢复的范围内。判断标准很简单：这次操作坏了，能不能用一个 `git` 命令回滚？不能，就不该给它全权限。

## 密钥不进对话

API key、数据库密码、私钥都不要粘贴进对话。需要它读配置时，让它读 `.env.example` 这类脱敏文件。万一泄露，第一件事是**立刻轮换**，而不是删聊天记录。同理，截图和日志在贴进去之前先扫一眼：连接串、token、内网地址经常藏在报错堆栈里。

> **注意：这几类命令要特别小心**
>
> - `rm -rf`：先 `ls` 确认路径，能进回收站就别直接删
> - `git reset --hard` / `git clean -fd`：未提交的工作会消失
> - `curl ... | sh`：先下载读一遍再执行
> - `npm publish`、`docker push`：会对外发布，确认版本与内容

## 让 agent 改代码前的检查

### 1. 工作区干净

`git status` 没有未提交改动，或已经 stash。这样出问题能一键回滚。

### 2. 开一条分支

在主分支上直接让 agent 改，回滚成本高。新开 feature 分支。

### 3. 限定范围

明确告诉它只改哪些目录，别碰配置和密钥文件。

### 4. 验收后再合并

测试通过、diff 看过、关键路径手动验一遍，再合并。

## 两种用法

| 图省事 | 稳妥 |
| --- | --- |
| 权限全开，弹窗全关 | 默认工作区写入，按需放宽 |
| 直接在主分支上改 | 每次改动开分支 |
| 密钥随手贴进对话 | 只用脱敏配置 |
| 它说完成就提交 | 测试 + diff + 手动验证 |

> 稳妥的做法多花几分钟，但把「不可恢复的事故」变成了「可以回滚的改动」。

> **提示：把检查写进项目**
>
> 在 `CLAUDE.md` / `AGENTS.md` 里写明：不要碰 .env、不要改锁文件、提交前必须跑测试。规则写在仓库里，比每次口头叮嘱可靠。

## 动手前的三行确认

```bash
$ git status
$ git switch -c agent/export-csv
$ git stash list
On branch main
nothing to commit, working tree clean
```

> `工作区干净、在新分支上、没有遗留的 stash。三行都确认过，再让 agent 开始改。`

## 出事之后怎么收场

`改动还没提交：`git restore` 或 `git checkout -- .`。已经提交但没推送：`git reset --soft` 回退后重做。已经推送：用 `git revert` 追加反向提交，不要改写公共历史。密钥泄露：先轮换，再清理历史。事后复盘时，把触发问题的那条命令写进 `AGENTS.md` 的禁区，比记在脑子里可靠。`

## 权限是会传染的

`团队里一个人开着全权限跑 agent，风险由整个仓库承担。把规则写进仓库配置，比依赖每个人的自觉更可靠。新成员入职时，把「默认沙箱 + 改前开分支」写成一条硬规矩，比事后追责有用，也更容易坚持。`

## 动手练一练

检查你当前项目的权限设置与 .gitignore，补上缺失的防护。

1. 确认 agent 的沙箱模式是工作区写入
2. 检查 .gitignore 是否包含 .env、node_modules、构建产物
3. 在 CLAUDE.md 或 AGENTS.md 里写三条「不要做」
4. 开一条分支，让 agent 做一次小改动并验收

**完成标准**：项目里没有任何密钥会被提交，改动可随时回滚。

## 小测验

<details>
<summary>展开题目与答案（3 题）</summary>

**1. agent 误删文件最常见的诱因是什么？**

- A. 模型有恶意
- B. 在错误的理解下执行了正确的命令
- C. 网络问题
- D. 磁盘故障

<details><summary>答案</summary>

**B**。风险通常来自理解偏差或路径写错，而不是模型主动作恶。沙箱与提交习惯能把影响限制住。

</details>

**2. 让 agent 改代码前，最该先做的是？**

- A. 关掉权限确认
- B. 确保工作区干净并开一条分支
- C. 把密钥发给它
- D. 直接在主分支改

<details><summary>答案</summary>

**B**。干净的工作区 + 独立分支，让任何改动都能回滚或丢弃。

</details>

**3. 密钥不小心泄露后，第一件事是？**

- A. 删掉聊天记录
- B. 立刻轮换密钥
- C. 重启电脑
- D. 改仓库名

<details><summary>答案</summary>

**B**。删除记录不能阻止已经泄露的凭据被使用；轮换才是止损。

</details>

</details>
