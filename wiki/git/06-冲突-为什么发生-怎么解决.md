# 冲突：为什么发生、怎么解决

> 两个人改了同一行，Git 停下来让你拍板

`Git 与版本控制` · 建议 15 分钟 · 进阶

## 学完这一节，你会

- 看懂冲突标记每一段是谁的版本
- 按编辑、add、commit 三步收尾
- 知道 merge --abort 与 rebase --continue 的差别
- 在冲突里不做会扩大损失的操作

## 冲突不是故障

冲突（conflict）的意思是：同一段内容被两边改成了不同的样子，Git 没有依据判断该留哪一个。它不会猜，直接把两版都塞进文件，让你决定。

所以看到 CONFLICT 不要慌，这只是流程里一个正常的停顿点。真正要做的事只有三件：打开文件、改成一个正确的版本、告诉 Git 你已经处理完。

冲突的范围通常很小，往往就是几行。Git 已经把两份内容摆在一起，你比它多知道的是业务上应该怎么选。

## 合并时撞上冲突

```bash
$ git merge feature/slow-api
Auto-merging src/request.js
CONFLICT (content): Merge conflict in src/request.js
Automatic merge failed; fix conflicts and then commit the result.
```

> Auto-merging 说明 Git 先自动合了一遍，能合的已经合好；CONFLICT 那行给出撞上的文件。此时合并处于「未完成」状态，不能切分支继续别的活。

## status 会告诉你还差什么

```bash
$ git status
On branch main
You have unmerged paths.
  (fix conflicts and run "git commit")
  (use "git merge --abort" to abort the merge)

Unmerged paths:
  (use "git add <file>..." to mark resolution)
	both modified:   src/request.js
```

> both modified 就是两边都改过的文件。Git 连补救命令都写在括号里：改完 git add，或者 git merge --abort 整个放弃。

## 冲突文件长什么样

```diff
function request(url) {
  const options = {
<<<<<<< HEAD
    timeout: 3000,
    retries: 1,
=======
    timeout: 5000,
    retries: 3,
>>>>>>> feature/slow-api
  };
  return fetch(url, options);
}
```

> 注意上下没被改动的行是干净的，只有冲突区间被包装起来。这些标记是文件里的真实字符，必须全部删掉，留下你选定的内容。

## 四组标记逐段解释

| 标记 | 含义 |
| --- | --- |
| <<<<<<< HEAD | 从这里开始是你当前所在分支的那一版 |
| ======= | 两侧内容的分界线 |
| >>>>>>> feature/slow-api | 到这里结束，这是被合并进来的那一版 |
| \|\|\|\|\|\|\| 8c1d0a7 | 只有开了 diff3 才出现，是两边共同的祖先版本 |

## 解决冲突的三步

### 1. 编辑文件，留一个正确的版本

不是二选一。你可以只留上面、只留下面，也可以两边都要再改写成一段新逻辑。删掉所有 &lt;&lt;&lt;&lt;&lt;&lt;&lt;、=======、&gt;&gt;&gt;&gt;&gt;&gt;&gt; 标记。

### 2. git add 标记为已解决

`git add src/request.js`。这一步是告诉 Git「这个文件我处理完了」，它才会进入下一次提交的内容里。

### 3. git commit 收尾

merge 场景用 `git commit --no-edit` 接受默认的合并信息；rebase 场景用 `git rebase --continue`，不要自己 commit。

## 收尾的样子

```bash
$ git add src/request.js && git commit --no-edit
[main 2f7c9a1] Merge branch 'feature/slow-api'
```

> 提交成功后合并结束，HEAD 回到正常状态。--no-edit 表示直接用默认的合并信息，不想用它就把 --no-edit 去掉，手动写说明。

## rebase 的冲突不一样

rebase 是把你的提交一个个重放到新基线上，所以它可能**冲突好几次**：解决完第一个，继续时下一个又撞上。

流程是：解决当前文件 → `git add` → `git rebase --continue`。中途想放弃，用 `git rebase --abort` 回到开始前的样子，一条命令全撤。

还有个反直觉的点：rebase 时 ours 指上游分支，theirs 指你正在重放的提交，和 merge 时的含义正好相反。用 `git checkout --ours 文件名` 之前先想清楚。

> **注意：冲突时别做的三件事**
>
> 一、别 `git commit -a` 直接盲提交。冲突标记会原样进仓库，页面上出现满屏的 &lt;&lt;&lt;&lt;&lt;&lt;&lt;。
>
> 二、别为了省事无脑 `git checkout --ours .`。那等于一键丢掉对方的全部改动，而且不报错、不提示，等对方发现时已经过去几天。
>
> 三、别在冲突没解决时 force push。合并未完成的状态下推送上去，远程会是坏掉的内容。

## 把冲突变少的具体做法

冲突无法根除，但可以变少：分支活得短，一条分支不超过两三天，越久越容易撞。

开工前先从主分支拉一次，把差异控制在小范围内。约定谁负责哪块文件，两个人同时大改同一文件必然冲突。

还有格式化：别人用 Prettier 跑一遍、你用编辑器自带格式化跑一遍，整文件都会变成冲突。团队统一格式化工具，并把它写进 .gitattributes 与编辑器配置。

> **提示：打开 diff3，看清祖先版本**
>
> `git config --global merge.conflictStyle zdiff3` 之后，冲突块里会多出 `|||||||` 那一段，显示两边共同祖先原本是什么样。
>
> 有了它你才能判断：这一行是对方删掉的，还是你新增的。只有两版而没有祖先版本时，很多人会把删除误当成修改。
>
> VS Code 里打开冲突文件会有 Accept Current Change、Accept Incoming Change、Accept Both 三个按钮，效果等于手工删标记，改完记得保存。

## 一次列出所有还冲突的文件

```bash
$ git diff --name-only --diff-filter=U
src/request.js
src/config.json
```

> U 表示 unmerged。文件多的时候别靠滚动 status 找，这条命令直接给出待处理清单。处理完一个就 add 一个，再跑一次看剩下的。

## 动手练一练

故意制造一次冲突：两条分支改同一个文件的同一行，合并时手工解决，再用 abort 重来一次看清退出路径。

1. 建仓库并在主分支写一行配置 —— `mkdir conflict-lab && cd conflict-lab && git init && printf "timeout=3000\n" > config.txt && git add . && git commit -m "chore: 初始配置"`
2. 开分支改成 5000 并提交 —— `git switch -c feature/slow && printf "timeout=5000\n" > config.txt && git commit -am "feat: 放宽超时"`
3. 切回 main 改成 1000 并提交，然后合并，观察冲突标记 —— `git switch main && printf "timeout=1000\n" > config.txt && git commit -am "fix: 收紧超时" && git merge feature/slow`
4. 看完标记后用 abort 退出，再重来一次手工解决并提交 —— `git merge --abort && git merge feature/slow`

**完成标准**：merge --abort 后 status 恢复干净；重新合并并手工改完后，add 加 commit 能顺利结束合并。

## 小测验

<details>
<summary>展开题目与答案（3 题）</summary>

**1. 冲突文件里 <<<<<<< HEAD 与 >>>>>>> feature/x 之间夹着的是什么？**

- A. Git 自动挑出来的推荐版本
- B. 你当前分支与被合并分支两侧的内容，需要你手工选或改写
- C. 冲突发生前的祖先版本
- D. Git 生成的一份补丁，可以直接应用

<details><summary>答案</summary>

**B**。标记之间先是 HEAD 一侧的内容，======= 之后是被合并分支的内容。Git 不做选择，把两版摆在一起等你决定，标记本身必须删干净。

</details>

**2. merge 冲突解决完之后，正确的收尾命令是什么？**

- A. git add 冲突文件，然后 git commit --no-edit
- B. git rebase --continue
- C. git merge --abort
- D. git commit -a 直接提交，让 Git 自己清理标记

<details><summary>答案</summary>

**A**。merge 的收尾是 add 标记已解决再 commit。rebase 才是 --continue，abort 是放弃，commit -a 会把冲突标记原样提交进仓库。

</details>

**3. rebase 过程中遇到冲突，想彻底放弃回到开始前的状态，用哪条命令？**

- A. git reset --hard 然后重新 pull
- B. git rebase --abort 回到 rebase 开始之前
- C. git merge --abort
- D. git checkout --theirs 全部覆盖

<details><summary>答案</summary>

**B**。rebase --abort 会把 HEAD 与分支还原到 rebase 开始时的位置，中间重放的提交一并撤销。merge --abort 只对应合并状态，用错会报 no merge in progress。

</details>

</details>
