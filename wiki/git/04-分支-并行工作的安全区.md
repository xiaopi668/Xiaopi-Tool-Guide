# 分支：并行工作的安全区

> 分支只是一根指针，合并要先站对位置

`Git 与版本控制` · 建议 14 分钟 · 基础

## 学完这一节，你会

- 说清分支为什么创建成本接近零
- 区分快进合并与三方合并的结果
- 记住合并方向：先切到要接收的分支
- 安全地删除已经合并的分支

## 分支不是复制一份代码

从「复制文件夹」习惯过来的人，常以为开分支等于把整个项目复制一遍。Git 里不是：分支就是一个写着提交哈希的文件，41 个字节，切换只是改 HEAD 指向哪一行。

所以「先开个分支试试」的成本几乎为零。验证一个思路、给客户做定制、同时修两个 bug，都可以直接开分支，不用考虑磁盘。

真正危险的不是分支本身，而是你对它的操作：切错分支改代码、在错误方向合并、删掉还没合并的分支。

## 看本机有哪些分支

```bash
$ git branch -vv
  feature/login  9a1c3f7 feat: 增加登录页
* main           4d8e2f1 [origin/main: ahead 1] docs: 补充第二节的例子
  fix/typo       8c1d0a7 chore: 初始化项目
```

> 星号是当前分支。-vv 顺带显示每个分支最后一条提交和跟踪关系，ahead 1 表示本地这条分支比远程多一条提交。

## 创建、切换、删除

```bash
git switch -c feature/login      # 从当前位置新建分支并切过去
git switch main                  # 切回 main
git switch -                     # 切回上一个分支，来回跳很方便
git branch -m old-name new-name  # 重命名分支
git branch -d feature/login      # 删除已合并的分支
git branch -D feature/login      # 强制删除，未合并的提交失去分支引用
```

> 老教程里的 git checkout -b 仍然能用，但 checkout 还能顺手切换文件内容，误操作代价大。2.23 之后优先用 switch 和 restore。

## merge 会得到三种结果

| 情况 | 合并结果 | 历史长什么样 |
| --- | --- | --- |
| main 上没有新提交 | 快进（fast-forward），只把指针挪过去 | 一条直线，不产生合并提交 |
| 两边都有新提交 | 三方合并（three-way merge），生成合并提交 | 分叉再合流，多一个合并节点 |
| 两边改了同一文件的同一行 | 冲突（conflict），合并停在半路等你处理 | 合并未完成，要 add 后再 commit |

## 情况一：快进

```bash
$ git switch main && git merge feature/login
Switched to branch 'main'
Updating 8c1d0a7..9a1c3f7
Fast-forward
 src/login.js | 42 ++++++++++++++++++++++++++++++++++++++
 1 file changed, 42 insertions(+)
```

> Fast-forward 说明这次只是把 main 的指针挪到 feature 的位置，没有产生新提交。前提是开分支之后 main 上没有别的提交，所以合并前先确认 main 是不是落后了。

## 情况二：三方合并

```bash
$ git merge feature/search
Merge made by the 'ort' strategy.
 src/search.js | 61 +++++++++++++++++++++++++++++++++++++++++++++++++++++
 1 file changed, 61 insertions(+)
```

> ort 是 Git 现在的默认合并策略，替代了旧的 recursive。看到 Merge made by 就说明生成了合并提交，而合并提交落在你当前所在的分支上。

## 方向：你想让谁变，就先站到谁那里

合并只有一条规则：**合并结果落在你当前所在的分支上**。所以「把 feature 并进 main」的正确顺序是：先站到 main 上，再 merge feature。

完整动作：`git switch main` → `git pull` 拿到远程最新 → `git merge feature/login` → `git push`。

搞反了会怎样：你在 feature 上 merge main，结果是 main 的新提交被拉进了 feature 分支，而 main 一点都没动。这时候 push 上去，PR 页面会显示一堆本不属于这个分支的提交，review 的人根本看不懂。

## 两种方向，两种结果

| 搞反：站在 feature 上 merge main | 正确：站在 main 上 merge feature |
| --- | --- |
| git switch feature/login 然后 git merge main | git switch main 然后 git pull 再 git merge feature/login |
| main 的提交被拉进 feature 分支 | 合并提交落在 main 上，历史清楚 |
| main 上仍然没有你的功能 | feature 分支不受影响，还能继续改 |
| PR 里混进别人的提交，review 无法进行 | PR 页面直接显示合并按钮 |
| 还得再合一次才能真正进 main | 合并后 git branch -d 删掉分支即可 |

> 一句话记法：你想让谁变，就先切到谁。想把功能合进 main，就站在 main 上敲 merge。

> **注意：删除分支的两种后果**
>
> `git branch -d` 是带检查的删除：分支上的提交如果还没合并进当前分支，它会拒绝，报 `error: The branch feature/login is not fully merged`。
>
> 加 `-D` 就跳过检查直接删。提交不会立刻消失，但失去分支引用之后，只能靠 reflog 或记住哈希找回，过了保留期就被回收。删之前先跑 `git log --oneline main..feature/login` 看一眼。
>
> 删除远程分支是另一条命令：`git push origin --delete feature/login`，这条会删掉所有人看到的那条分支引用。

## 哪些分支已经合并了

```bash
git branch --merged                    # 已合并进当前分支，可以安全删
git branch --no-merged                 # 还没合并，删之前先看内容
git log --oneline main..feature/login  # 这个分支上有哪些 main 没有的提交
```

> --merged 判断的是相对当前分支。你现在站在 main 上，看到的就是已经合进 main 的分支列表。

## 一次完整的特性分支流程

### 1. 从最新的 main 开分支

`git switch main && git pull && git switch -c feature/login`。先 pull 再开分支，能少一次后面的合并冲突。

### 2. 小步提交

每完成一个可验证的小块就 commit 一次。分支上的提交可以随便改，合并进 main 之后就不能随便动了。

### 3. 合并前先让 main 追上远程

切回 main，`git pull`，再 `git merge feature/login`。团队协作时这一步通常在 GitHub 上以 PR 形式完成。

### 4. 删除分支并推送

`git branch -d feature/login`，然后 `git push`。分支删了，提交依然在 main 的历史里。

> **提示：main 上不要直接写代码**
>
> 把 main 当成发布线：它上面永远是可用的状态。所有改动从分支进，测试过了才合并。
>
> GitHub 仓库可以在 Settings → Branches 里给 main 加保护规则：禁止直接推送、必须走 PR、必须通过 CI。开了保护之后，误操作在服务端就被拦住，比靠自觉可靠。
>
> 一个人写的小项目也建议这么干。你今天省下的那一次切分支，往往就是半年后翻不出来的那次改动。

## 动手练一练

在一个有两个提交的仓库里开分支、改文件、合并回 main，再从 merged 列表里确认它已经安全合并。

1. 建仓库并提交一次，作为 main 的起点 —— `mkdir branch-lab && cd branch-lab && git init && echo v1 > app.txt && git add . && git commit -m "chore: 初始化"`
2. 开分支、改文件、提交 —— `git switch -c feature/greeting && echo hello >> app.txt && git commit -am "feat: 增加问候语"`
3. 切回 main 合并，观察是否出现 Fast-forward —— `git switch main && git merge feature/greeting`
4. 确认哪些分支已合并，再安全删除 —— `git branch --merged && git branch -d feature/greeting && git log --oneline --graph --all`

**完成标准**：合并输出里出现 Fast-forward，branch --merged 能看到那条分支，删掉后历史仍在。

## 小测验

<details>
<summary>展开题目与答案（3 题）</summary>

**1. git switch -c feature/x 之后，feature/x 与 main 的关系是什么？**

- A. 两条指向同一个提交的指针，HEAD 现在指向 feature/x
- B. feature/x 复制了 main 的全部文件，之后互不影响
- C. feature/x 是 main 的只读副本，改动会同步回去
- D. main 被暂时隐藏，切回去时自动恢复

<details><summary>答案</summary>

**A**。新分支从当前提交起步，一开始和 main 指向同一个位置。此后各自的 commit 只移动自己的指针，另一个分支原地不动，两条线才会慢慢分开。

</details>

**2. 你在 feature/login 分支上执行 git merge main，会发生什么？**

- A. main 得到 feature/login 的提交，直接可以推送
- B. main 的提交被合进 feature/login，main 本身没有任何变化
- C. 两条分支互换内容
- D. Git 会拒绝执行，因为方向错误

<details><summary>答案</summary>

**B**。合并结果永远落在当前分支上。站在 feature 上 merge main，只是把 main 的提交拉进来，main 本身一点没变，要等你切回去再合一次才会更新。

</details>

**3. git branch -d 报 error: The branch is not fully merged，说明什么？**

- A. 分支已经被远程删除，本地还留着
- B. 分支上有提交还没合并进当前分支，删了会失去引用
- C. 分支名拼写错误
- D. 仓库处于分离头指针状态

<details><summary>答案</summary>

**B**。-d 会先检查是否已合并。这个报错是保护机制，先 git log main..分支名 看内容，确认不要了再用 -D 强删。

</details>

</details>
