# 远程仓库与协作

> fetch、pull、push 到底谁动了你的文件

`Git 与版本控制` · 建议 15 分钟 · 基础

## 学完这一节，你会

- 看清 remote、origin 与跟踪分支的关系
- 分清 fetch 与 pull 的副作用
- 读懂 -u 写入的两行配置
- 独立走完一次 fork 到 PR 的流程

## 远程只是一个地址

远程仓库（remote）不是别人替你托管的一台机器，它只是你本地仓库里存着的一个名字加一个地址。默认名字叫 origin，指向 GitHub、GitLab 或公司内网的某个仓库。

`git push` 不是「上传文件夹」，而是把本地的新提交送过去，再把远程那条分支指针往前挪。`git fetch` 反过来，把远程的新提交拉下来。

一个仓库可以挂多个远程：origin 指向你自己的 fork，upstream 指向原项目。名字只是别名，命令里写哪个都行。

## 先看挂了哪些地址

```bash
$ git remote -v
origin	git@github.com:lin/blog.git (fetch)
origin	git@github.com:lin/blog.git (push)
upstream	git@github.com:team/blog.git (fetch)
upstream	git@github.com:team/blog.git (push)
```

> 同名两行是同一个仓库，分别用于 fetch 和 push。fork 场景下 origin 是你自己的仓库，upstream 是原项目，PR 就是从前者提到后者。

## clone 下来的到底是什么

clone 不是下载最新一版文件。它下载**全部历史**，然后做四件事：创建 origin 远程；把默认分支检出到工作区；让本地 main 跟踪 origin/main；留下一个只读的远程分支引用 origin/main。

origin/main 不是你能提交的分支，它是「上次同步时远程长什么样」的本地快照。你能动的只有本地 main。

所以 clone 完直接改代码、commit 是安全的，提交先落在本地。要等到 push，远程才看得见。

## 第一次推送记得带 -u

```bash
$ git push -u origin main
Enumerating objects: 12, done.
Writing objects: 100% (7/7), 1.21 KiB | 1.21 MiB/s, done.
To github.com:lin/blog.git
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.
```

> 最后一行是关键：-u 顺手把本地 main 和 origin/main 绑成跟踪关系。此后 git push 和 git pull 都不用再写 origin main。

## -u 改的是哪两行

`-u` 是 `--set-upstream` 的简写。它往 `.git/config` 里写 `branch.main.remote=origin` 和 `branch.main.merge=refs/heads/main` 两条。

写完之后的三个变化：`git push` 不带参数也知道往哪推；`git pull` 知道从哪拉；`git status` 能告诉你 ahead 2、behind 1。

没带 -u 的典型报错：`fatal: The current branch main has no upstream branch`，下面会直接给出补救命令 `git push --set-upstream origin main`，照抄即可。

## 三条命令，各自动了什么

| 命令 | 下载远程提交 | 改你的工作区 | 会不会多出合并提交 |
| --- | --- | --- | --- |
| git fetch | 会 | 不会，一行不动 | 不会 |
| git pull | 会 | 会，用 merge 合进来 | 本地有分叉时会 |
| git pull --rebase | 会 | 会，把本地提交重放一遍 | 不会，但本地提交的哈希会变 |

## fetch 与 pull 的分界线

`git fetch` 只更新 origin/main 这个引用和一堆对象，工作区、暂存区、本地 main 全都不动。它没有副作用，随便跑。

`git pull` 等于 fetch 加 merge：拉下来之后立刻合进你当前分支，所以它可能冲突，也可能弹出编辑器让你写合并说明。

代码改到一半、跑一半的测试还挂着的时候不要 pull。想看远程有什么新东西，先 fetch，再用 `git log --oneline HEAD..origin/main` 看差了多少。

## fetch 之后只动了引用

```bash
$ git fetch
remote: Enumerating objects: 12, done.
remote: Counting objects: 100% (12/12), done.
From github.com:lin/blog
   8c1d0a7..4d8e2f1  main       -> origin/main
```

> 箭头表示 origin/main 从 8c1d0a7 前进到 4d8e2f1，被更新的只有这个引用。你自己的 main 还停在原地，这就是 fetch 安全的原因。

> **注意：推送被拒不是网络问题**
>
> 完整报错：`! [rejected] main -> main (non-fast-forward)`，下面跟 error: failed to push some refs to 地址，还有一行提示先 pull。
>
> 原因：远程有你本地没有的提交，直接推会盖掉别人的工作，Git 拦住你。正确做法是 `git pull --rebase`，处理可能的冲突，再 push。
>
> 不要用 `--force` 消掉这个报错。它会把远程退回到你的版本，同事的提交从分支上消失，对方得自己去 reflog 里捞。只有你自己独占的分支才谈得上 `--force-with-lease`。

## 跟踪分支：ahead 与 behind 的来源

跟踪分支（tracking branch）就是本地分支与某个远程分支绑在一起。看谁和谁绑着：`git branch -vv`，方括号里那段就是。

远程已经有的分支，直接 `git switch feature/login` 就会建同名本地分支并自动跟踪 origin/feature/login，不用手写。

status 里的 ahead 和 behind 是判断要不要推、要不要拉的全部依据，比凭感觉靠谱。

## 在 GitHub 上开一个 PR

### 1. fork 并 clone 自己的那份

在项目页点 Fork，然后 `git clone git@github.com:你的用户名/blog.git`。如果想让本地能同步原项目，再加一个 upstream：`git remote add upstream git@github.com:team/blog.git`。

### 2. 从最新 main 开一条功能分支

`git switch main && git pull && git switch -c feature/fix-typo`。分支名要能看出做什么，别用 test、dev、新分支。

### 3. 提交并推送

小步 commit，然后 `git push -u origin feature/fix-typo`。第一次推送的输出里会带一条 GitHub 的链接，直接点开就是创建 PR 的页面。

### 4. 写清 PR 描述

标题说明改了什么，正文写动机、做法、怎么验证（跑了哪条命令、点了哪个页面）。截图能省掉一半来回。关联 issue 写 Closes #12。

### 5. 等 review，合并，收尾

reviewer 提了意见就继续 commit 再 push，PR 会自动更新。通过后点 Squash and merge，删掉远程分支，回到本地 `git switch main && git pull`。

> **提示：把 pull --rebase 设成默认**
>
> `git config --global pull.rebase true` 之后，pull 会把你的本地提交挪到远程提交后面，而不是生成一条「Merge branch main of github.com」的合并提交。
>
> 代价是你本地还没推的提交哈希会变。所以规则要一致：已经推送到共享分支的提交，不要 rebase。
>
> 每天开工先 pull 一次，收工前 push 一次。这两条做到，八成「代码不见了」的惊慌不会发生。

## 动手练一练

用两个本地仓库模拟远程：一个当服务器，一个 clone 下来，走一遍改、推、拉，再看清 fetch 与 pull 的区别。

1. 建一个裸仓库当作远程，再 clone 到工作目录 —— `git init --bare /tmp/blog-remote.git && git clone /tmp/blog-remote.git blog`
2. 在 clone 里提交并首次推送，注意跟踪关系 —— `cd blog && echo hi > README.md && git add . && git commit -m "docs: 第一条提交" && git push -u origin main`
3. 在另一个 clone 里提交推送，回到第一个仓库只 fetch 不合并 —— `git fetch && git status -sb && git log --oneline HEAD..origin/main`
4. 确认工作区没变之后，再 pull 把变化合进来 —— `git pull --rebase && git log --oneline --graph --all`

**完成标准**：fetch 之后 status 显示 behind，但文件内容没变；pull 之后文件才被更新。

## 小测验

<details>
<summary>展开题目与答案（3 题）</summary>

**1. git push -u origin main 里的 -u 做了什么？**

- A. 强制推送，覆盖远程已有的提交
- B. 把本地 main 与 origin/main 绑定为跟踪关系，之后 push 可省略参数
- C. 在远程创建一个空的 main 分支但不推送内容
- D. 切换到远程分支的只读副本

<details><summary>答案</summary>

**B**。-u 即 --set-upstream，写进 .git/config 两行跟踪配置。绑定之后 git push、git pull 都不用再写远程名和分支名，status 也会显示 ahead 与 behind。

</details>

**2. 为什么说 git fetch 比 git pull 安全？**

- A. fetch 会先备份工作区再合并
- B. fetch 只更新 origin/main 等远程引用，不碰工作区和本地分支
- C. fetch 会自动跳过有冲突的文件
- D. fetch 会把改动存到暂存区，等你确认

<details><summary>答案</summary>

**B**。fetch 只下载对象并移动 origin/ 开头的引用，本地分支与工作区都不动。pull 是 fetch 加 merge，会直接改你正在编辑的文件。

</details>

**3. push 报 ! [rejected] main -> main (non-fast-forward)，正确的处理顺序是？**

- A. 直接 git push --force 覆盖远程
- B. 先 git pull --rebase 把远程提交接上，解决冲突后再 push
- C. 删除本地仓库重新 clone
- D. 把远程分支删掉再重建

<details><summary>答案</summary>

**B**。被拒说明远程有你没有的提交。先拉下来把自己提交重放到后面，冲突当场解决，再推送就是快进，别人的工作一条都不会丢。

</details>

</details>
