# 后悔药：撤销与回滚

> 改错了、提交早了、推错了，分别该用哪条命令

`Git 与版本控制` · 建议 18 分钟 · 进阶

## 学完这一节，你会

- 分清工作区、暂存区、历史三种撤销
- 知道 restore、reset、revert 各自的边界
- 误删提交时能用 reflog 把它找回来

## 三种「撤销」，其实是三件事

Git 里没有统一的一个「撤销」按钮，因为你的改动可能停在三个不同的地方：**工作区**（你眼前正在编辑的文件）、**暂存区**（下一次提交的清单）、**历史**（已经提交的快照）。

在哪一层出的错，就要用哪一层的命令去撤。用错层的典型后果是：想撤掉一次提交，结果把一整天没提交的代码一起删了。

所以动手前先跑一次 `git status`，看清楚每个文件现在处于哪个状态，再决定用哪条命令。

## 我想撤销什么，该用哪条

| 我想撤销… | 命令 | 会不会丢东西 |
| --- | --- | --- |
| 工作区里还没 add 的改动 | git restore 文件名 | 会丢，而且不进回收站 |
| 文件在暂存区里（改动保留） | git restore --staged 文件名 | 不会丢，改动回到工作区 |
| 最后一次提交（改动保留） | git reset --soft HEAD~1 | 不会丢，改动留在暂存区 |
| 最后一次提交和全部改动 | git reset --hard HEAD~1 | 会丢，几乎无法恢复 |
| 一条已经推送的提交 | git revert 提交号 | 不会丢，会生成一条反向提交 |
| 误删的分支或提交 | git reflog，再 git branch 恢复 | 通常能找回 |

## 丢弃工作区里的改动

```bash
$ git diff src/app.js
$ git restore src/app.js
diff --git a/src/app.js b/src/app.js
-const port = 3000;
+const port = 3001;
```

> 先用 `git diff` 看清要丢的是什么，再 restore。这一步没有确认提示，执行完就回不去了。

## 只把文件移出暂存区

```bash
$ git restore --staged src/app.js
$ git status -sb
 M src/app.js
```

> 注意状态列的位置：`M ` 在第一列表示「已暂存」，` M` 在第二列表示「工作区有改动但没暂存」。一排空格的位置就是这一列的含义。

## reset 的三种模式，只差在重置到哪一层

三条命令都移动 HEAD，区别只是顺带重置了哪些区域：

- **--soft**：只移动 HEAD，暂存区和工作区不动。改动还在暂存区里，适合「提交信息写错了，想重新提交一次」。
- **--mixed**（默认）：移动 HEAD 并清空暂存区，工作区不动。改动变回未暂存状态。
- **--hard**：三者一起重置。工作区的改动直接消失。

记住一句话：**reset 是改写本地历史，只适合还没推送的提交**。

## 已经推送的提交，不要用 reset

| 错误做法 | 正确做法 |
| --- | --- |
| git reset --hard 之后 git push --force | git revert 提交号，生成一条反向提交 |
| 队友本地的历史和你对不上，pull 下来一片混乱 | 历史只增不改，所有人都能正常 pull |
| 强制推送会覆盖别人基于这条分支做的工作 | 评审记录完整保留，谁撤的、为什么撤一目了然 |
| 代码评审记录里的提交凭空消失 | 真需要强制推送时，至少用 --force-with-lease |

> 原则：**本地没推送的历史可以改写，已经推送的历史只能追加**。别人可能已经拉过那条提交，改写等于把他们的历史和你的历史劈成两条。

## revert 一条已经推送的提交

```bash
$ git revert 3f2a9c1
[main 8c41d20] Revert "feat: 首页加登录横幅"
 1 file changed, 3 deletions(-)
```

> revert 不会删掉原来那条提交，而是新增一条把它的效果抵消掉的提交。历史里两条都在，因果关系清楚。

## 误删提交后，用 reflog 找回来

### 1. 先看 reflog

`git reflog` 记录的是 HEAD 的每一次移动，包括 reset、merge、切分支。找到那条被删提交的短 SHA。

### 2. 确认内容是对的

`git show 3f2a9c1` 看一眼提交信息和文件改动，别救错。

### 3. 挂一个分支把它固定住

`git branch rescue 3f2a9c1`。这比直接 reset 安全，原来的分支状态一点不动。

### 4. 确认无误再合并回来

`git merge rescue`，或者 cherry-pick 你真正需要的那一条。

> **注意：reset --hard 是这里唯一真正危险的命令**
>
> 它会同时重置 HEAD、暂存区和工作区。已经提交过的内容理论上还能靠 reflog 捞回来，但**从未提交过的工作区改动，Git 根本不认识，丢了就是丢了**。
>
> 执行前至少做一件事：`git status` 确认没有未提交的改动，或者先 `git stash` 收起来。

> **提示：拿不准的时候，先备份再动手**
>
> 最省事的保险：把整个项目目录复制一份，或者在干净状态下 `git stash`。这些操作比事后找数据便宜得多。
>
> 另外，`git reflog` 默认保留 90 天，足够你反应过来。

## 动手练一练

在一个随便建的练习仓库里，把工作区、暂存区、历史三种撤销各做一遍，亲手感受它们的区别。

1. 改一个文件后用 git diff 看清改动，再丢弃它 —— `git restore .`
2. 再改一次，git add 之后移出暂存区，确认改动还在 —— `git restore --staged .`
3. 提交这次改动，用软重置撤销提交，确认改动回到暂存区 —— `git reset --soft HEAD~1`
4. 用 reflog 找到刚才那条提交的短 SHA —— `git reflog`

**完成标准**：能用一句话说清 restore、reset --soft、revert 各自改变的是哪个区域。

## 小测验

<details>
<summary>展开题目与答案（3 题）</summary>

**1. 一条已经推送到远程、同事也拉过的提交写错了，应该怎么撤？**

- A. git reset --hard 退回上一个提交，然后强制推送
- B. git revert 那条提交，生成一条反向提交
- C. git commit --amend 改掉它，再正常 push
- D. 删掉远程仓库重新建一个

<details><summary>答案</summary>

**B**。已推送的历史不要改写，revert 通过追加一条反向提交来抵消效果，所有人的历史依然一致。reset 加强制推送会让同事的本地历史对不上。

</details>

**2. 执行 git reset --soft HEAD~1 之后，你刚才的改动在哪里？**

- A. 已经被删除，需要重新写
- B. 回到工作区，处于未暂存状态
- C. 还在暂存区里，可以直接重新提交
- D. 已经推送到了远程仓库

<details><summary>答案</summary>

**C**。--soft 只移动 HEAD，不碰暂存区和工作区，所以改动仍然停留在暂存区，改一句提交信息就能重新提交。--mixed 才是退回工作区。

</details>

**3. 误删了一个还没合并的分支，最可能把它找回来的第一步是？**

- A. git reflog，找到那个提交的 SHA
- B. git log --all，直接列出被删的分支
- C. git restore --staged 分支名
- D. 重新 clone 一遍远程仓库

<details><summary>答案</summary>

**A**。reflog 记录了 HEAD 的移动轨迹，分支删掉后提交对象通常还在。找到 SHA 后用 git branch 名字 SHA 就能恢复。log --all 只显示还挂着的引用。

</details>

</details>
