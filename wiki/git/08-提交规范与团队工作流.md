# 提交规范与团队工作流

> 让别人（和三个月后的你）看得懂这些提交

`Git 与版本控制` · 建议 15 分钟 · 进阶

## 学完这一节，你会

- 把一次提交控制在只做一件事
- 写出能一眼看懂的提交信息
- 走通一个功能分支从开工到合并的流程

## 提交信息是写给未来的

三个月后你会回来查：「这行代码为什么这么改？」如果提交信息写的是「改一下」「fix」，你只能逐行读 diff。如果写的是「fix(login): 修复验证码过期后仍可提交」，三秒就能定位。

提交信息不是给 Git 看的，是给**排查问题的人**看的。而那个人大概率是你自己。

## 一次巨型提交 vs 小步提交

| 一次大提交 | 小步提交 |
| --- | --- |
| 一条提交里有登录、样式和依赖升级 | 每条提交只做一件事，说明写清做了什么 |
| 出问题时不知道是哪部分引起的 | 出问题可以用 bisect 精确定位到某一条 |
| 想单独回滚登录功能，只能手工挑代码 | 回滚一条提交就是回滚一个功能 |
| diff 上千行，评审的人直接点通过 | diff 小，评审真的会看 |

> 判断标准很简单：**能不能用一句话说清这条提交做了什么；出问题时能不能单独撤掉它而不影响别的**。两个都能，就够小了。

## 一条提交只做一件事

常见误区是把「改 bug」和「顺手格式化整个文件」放在一条提交里。结果回滚 bug 修复时，格式化也跟着被撤掉，diff 里一半是空格变化。

如果确实顺手改了很多地方，用 `git add -p` 分块暂存，或者分几次提交。提交数量多一点不是问题，混乱才是。

## 提交信息的结构

```text
类型(范围): 一句话说明做了什么

可选正文：为什么这么改，而不是怎么改（代码本身已经说明怎么改）

可选脚注：关联 issue，例如 Closes #128
```

> 第一行控制在 50 个字符以内，用祈使句（「修复」「新增」），结尾不加句号。正文和标题之间空一行。

## Conventional Commits 的常见类型

| 类型 | 含义 | 例子 |
| --- | --- | --- |
| feat | 新增功能 | feat(auth): 支持邮箱验证码登录 |
| fix | 修复缺陷 | fix(upload): 修复大文件上传超时 |
| docs | 只改文档 | docs: 补充本地启动步骤 |
| refactor | 重构，不改行为 | refactor(api): 抽出统一的请求封装 |
| test | 新增或修改测试 | test(cart): 补充金额计算的边界用例 |
| chore | 杂项：依赖、配置、脚本 | chore: 升级 vite 到 6.0 |
| perf | 性能优化 | perf(list): 长列表改为虚拟滚动 |

## 分支命名：让人一眼知道它要干什么

推荐用「类型/简短描述」：`feature/login-page`、`fix/upload-timeout`、`chore/bump-deps`。全小写、用短横线连接，不要用中文、空格和日期。

分支名会出现在 PR 列表、CI 日志和别人的终端里，它是一条信息，不是随手起的文件夹名。

## 一个功能从开工到合并

### 1. 先同步主干

`git switch main && git pull`，保证你是从最新的代码开分支。

### 2. 开一条短分支

`git switch -c feature/login-page`。分支生命周期越短，冲突越少。

### 3. 小步提交

每完成一小块就提交一次，信息按上面的格式写。提交前 `git diff --staged` 自查一遍。

### 4. 推送并开 PR

`git push -u origin feature/login-page`，然后在平台上发起 Pull Request，写清改了什么、怎么验证。

### 5. 评审通过后合并并删分支

合并后删掉远端分支，本地 `git branch -d` 清理，回到 main 再 pull 一次。

## 提交前的三行自查

```bash
$ git status -sb
$ git diff --staged
$ git log --oneline -5
## feature/login-page
 M src/login.js

+ export function login() {
```

> 第一行看分支和文件状态，第二行看即将提交的完整改动，第三行看最近五条提交，确认风格一致、没有重复提交。

> **注意：这些东西永远不要提交**
>
> `.env` 和各种密钥、`node_modules`、构建产物、个人编辑器配置、几百 MB 的素材文件。
>
> 如果已经提交过一次，光加 .gitignore 是不够的——文件还在历史里。正确顺序是：**立刻轮换泄露的密钥**，然后 `git rm --cached 文件` 提交移除，再补上 .gitignore。历史里的旧版本仍然需要清理工具处理。

## 主干开发，还是 Git Flow

小团队和大多数项目用**主干开发**就够了：只有 main 一条长期分支，功能分支活一两天，通过 PR 合并，合并即部署。

Git Flow 那套 develop / release / hotfix 分支，适合发布周期固定、需要同时维护多个线上版本的项目。多一层分支就多一层同步成本，没有对应需求时不要照搬。

> **提示：发 PR 之前问自己四个问题**
>
> - 这个 PR 只做一件事吗？能不能用一句话说清？
> - diff 里有没有混进调试代码、注释掉的旧逻辑、无关的格式化？
> - 别人拿到这个分支，知道怎么跑起来、怎么验证吗？
> - 有没有提交不该进仓库的文件？

## 动手练一练

找一个你自己的仓库，把最近一次提交改成规范写法，再按规范开一条新分支。

1. 用 amend 把最近一次提交的信息改成「类型(范围): 说明」格式 —— `git commit --amend`
2. 按规范新建一条功能分支 —— `git switch -c feature/your-task`
3. 检查 .gitignore 里是否包含 .env 和 node_modules
4. 用 git log --oneline -5 回头看这五条信息是否都能看懂

**完成标准**：提交历史里每一条都能让局外人看懂做了什么，分支名能看出要做什么。

## 小测验

<details>
<summary>展开题目与答案（3 题）</summary>

**1. 提交信息「feat(auth): 支持邮箱验证码登录」里的 feat 表示什么？**

- A. 修复了一个缺陷
- B. 新增了一个功能
- C. 只改了文档
- D. 重构了代码结构

<details><summary>答案</summary>

**B**。feat 是 feature 的缩写，表示新增功能。fix 是修复，docs 是文档，refactor 是不改变行为的重构。

</details>

**2. 把三个互不相关的改动塞进同一条提交，最大的问题是什么？**

- A. 提交信息会超过一行
- B. 出问题时无法单独回滚其中一项
- C. Git 会拒绝提交
- D. 推送速度会变慢

<details><summary>答案</summary>

**B**。提交是回滚的最小单位。混在一起，想撤掉其中一项就只能手工挑代码，而且评审时 diff 太大容易被直接放过。

</details>

**3. 团队采用主干开发时，功能分支应该保持什么状态？**

- A. 长期保留，作为功能开发的独立空间
- B. 生命周期尽量短，完成后尽快合并回主干
- C. 直接在 main 上开发，不需要分支
- D. 只在本地存在，永远不推送

<details><summary>答案</summary>

**B**。分支活得越久，和主干分叉越远，合并冲突越难处理。主干开发的关键就是短分支、频繁合并、合并即部署。

</details>

</details>
