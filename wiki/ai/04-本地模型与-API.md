# 本地模型与 API

> 数据不出机器，以及 token 是怎么烧钱的

`AI 时代` · 建议 12 分钟 · 进阶

## 学完这一节，你会

- 分清本地模型和云服务的取舍
- 用 Ollama 在本地跑一个模型
- 知道 API key 与成本的基本管理

## 两种运行方式

**云服务**：模型在别人的机房里，能力强、免维护，按用量收费，数据要传出去。**本地模型**：模型下载到你自己的电脑，数据不出机器，免费，但吃显存、能力弱一些。

## 怎么选

| 维度 | 云服务 | 本地模型 |
| --- | --- | --- |
| 能力 | 强，支持长上下文与工具 | 中等，适合摘要、改写、分类 |
| 隐私 | 数据上传，看条款 | 不出机器 |
| 成本 | 按 token 计费 | 电费与硬件 |
| 速度 | 取决于网络 | 取决于显卡/内存 |
| 维护 | 无需 | 要装运行时、下模型 |

## 用 Ollama 跑本地模型

```bash
$ ollama --version
$ ollama pull llama3.2
$ ollama run llama3.2
pulling manifest
success
>>> Send a message (/? for help)
```

> 模型名换成你想要的即可（如 `qwen3`、`llama3.2`）。第一次拉取要下载几个 GB，之后离线可用。

## 硬件与模型大小

模型参数量越大，能力越强，占的内存也越多。8B 级别在 16GB 内存的笔记本上能跑，70B 级别通常需要专业显卡。先跑小的，够用就别追大。

## API 与 token

调用云模型 API 时，计费单位是 token（大约一个汉字一到两个）。**输入和输出都算钱**，长文档和长对话都会迅速累积。批量任务先估算：单次 token × 次数 × 单价。

## API key 放环境变量，不要写进代码

```bash
# ~/.zshrc 或 ~/.bashrc
export MODEL_API_KEY="sk-..."

# 代码里读取
# const key = process.env.MODEL_API_KEY;
```

> 把 `.env` 加进 `.gitignore`。密钥一旦提交，就会永久留在 git 历史里，只能轮换。

> **注意：本地模型不是缩小版的大模型**
>
> 小模型在复杂推理、长文一致性、工具调用上明显更弱。适合摘要、分类、改写、离线问答；不适合让它独立完成多步推理或写生产代码。

> **提示：先用本地做草稿，再用云做精修**
>
> 敏感材料先在本地脱敏、摘要，再把不含敏感信息的结果交给云模型润色。既省 token，又降低泄露风险。

## 直接调 API 看一眼成本

```bash
$ curl https://api.example.com/v1/chat/completions \
$   -H "Authorization: Bearer $MODEL_API_KEY" \
$   -H "Content-Type: application/json" \
$   -d '{"model":"your-model","messages":[{"role":"user","content":"用一句话解释什么是 token"}]}'
{"usage":{"prompt_tokens":18,"completion_tokens":24,"total_tokens":42}}
```

> @@响应里的 `usage` 就是这次的计费依据。批量任务先用一条请求估算单价，再乘次数。@@

## 算一笔账

@@假设一次请求输入 2000 token、输出 500 token，单价按每百万 token 几元到几十元不等。跑 1000 次之前，先用一条请求看 `usage`，乘出来再决定要不要批处理、要不要换更小的模型。长文档最贵的是输入：把整份 PDF 反复贴进对话，等于每次都重新付费。先摘要成要点，再带着要点提问。需要反复问同一份材料时，把摘要存下来复用。批量任务先跑十条样本，确认质量可接受再全量，避免把预算花在错误的方向上。@@

## 本地部署的边界

@@本地模型适合：敏感材料的摘要与分类、离线环境、固定的格式转换。不适合：需要最新知识、需要调用工具、需要长链条推理的任务。显存不够时会自动切到内存，速度骤降；先确认模型大小和机器匹配，再谈体验。跑不动就换更小的量化版本。量化（4bit/8bit）能显著降低显存占用，代价是精度略降；先试量化版，跑得动再考虑原版，别一上来就下载最大的，够用就够了。如果只是偶尔用一次，云服务更划算；本地适合高频、敏感、离线、数据不出门的场景。@@

> **提示：把敏感处理留在本地**
>
> @@流程可以是：本地模型脱敏与摘要 → 只把脱敏后的文本交给云模型润色 → 人工合并。多一步，但泄露风险小很多。@@

## 动手练一练

在本机跑起一个本地模型，比较它和云模型在同一段摘要任务上的差别。

1. 安装 Ollama 并拉一个 8B 级模型 —— `ollama pull llama3.2`
2. 让它摘要一段 500 字的材料
3. 用云模型做同样的任务，比较质量与速度

**完成标准**：能说清本地模型适合什么、不适合什么。

## 小测验

<details>
<summary>展开题目与答案（3 题）</summary>

**1. 本地模型最大的优势是？**

- A. 能力更强
- B. 数据不出机器
- C. 不需要显卡
- D. 支持更长上下文

<details><summary>答案</summary>

**B**。本地推理的数据留在自己机器上，适合敏感材料；代价是能力与速度。

</details>

**2. API 计费通常按什么单位？**

- A. 请求次数
- B. token 数
- C. 文件大小
- D. 运行时长

<details><summary>答案</summary>

**B**。输入与输出都按 token 计费，长文档和长对话会迅速累积成本。

</details>

**3. API key 应该放在哪里？**

- A. 直接写进代码
- B. 提交到仓库方便协作
- C. 环境变量或密钥管理服务
- D. 发在群里

<details><summary>答案</summary>

**C**。密钥进仓库就会永久留在历史里；用环境变量或专门的密钥管理，并加进 .gitignore。

</details>
