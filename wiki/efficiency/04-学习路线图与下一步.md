# 学习路线图与下一步

> 把这一站学过的东西接成一条能自己往前走的线

`效率与排错` · 建议 10 分钟 · 进阶

## 学完这一节，你会

- 说清从终端到部署的七个阶段
- 给自己排出每天二十分钟的练法
- 用三个小项目检验学到的工具
- 遇到新工具时知道先去哪里查

## 一条线，七个站

这些工具不是七门独立的课，是同一条流水线上的七个环节：你在**终端**里敲命令，用 **Git** 把改动存成能回退的历史，在**编辑器**里写代码，用**一门语言**把想法写成程序，用**包管理器**借别人的轮子，靠**调试**弄明白它为什么不按你想的跑，最后**部署**出去让别人真的用上。

顺序有意义：后一步都在用前一步。跳过终端直接学框架，会在「命令跑不起来」上卡住；不学 Git 就写项目，会在改坏之后没法回头。卡住的时候往回退一站，通常比硬着头皮往前冲快。

## 全景：七个阶段与判断标准

| 阶段 | 要学的东西 | 学会的标志 | 大概用时 |
| --- | --- | --- | --- |
| 终端 | 路径、管道、权限、进程 | 不看教程能起服务、查端口、读日志 | 1-2 周 |
| Git | add、commit、branch、merge、rebase | 敢开分支，能读懂 git log --graph | 2-3 周 |
| 编辑器 | 快捷键、搜索、多光标、插件 | 全程不碰鼠标改完一个文件 | 1 周起步，长期打磨 |
| 一门语言 | 语法、数据结构、错误处理 | 能读写文件、发 HTTP 请求、处理异常 | 1-2 个月 |
| 包管理 | 依赖、锁文件、版本范围 | 能解释 package-lock 为什么要提交 | 1 周 |
| 调试 | 断点、日志、栈追踪、最小复现 | 能从报错定位到具体那一行 | 2-3 周 |
| 部署 | 构建、环境变量、域名、日志 | 把自己的项目挂上公网并看到访问日志 | 2 周 |

## 每天二十分钟，比周末五小时管用

技能是肌肉记忆，靠频率而不是靠单次时长。每天二十分钟连做三周，比周末一次性看五小时教程有效得多——后者看完就忘，因为手没动过。

二十分钟切成四段：前五分钟复述昨天做了什么，中间十分钟只做一件具体的事，接着三分钟读官方文档里相关的那一节，最后两分钟写下今天卡在哪里、明天第一步做什么。四段时间到点就停，不用延长。

## 二十分钟怎么排

### 1. 复述昨天（5 分钟）

合上笔记，用自己的话讲一遍昨天那条命令做了什么。讲不出来的地方就是没学会的地方，今天先补它，别往前赶。

### 2. 只做一件事（10 分钟）

这件事要小到当天能做完：把别名写进配置文件并验证生效、给仓库开一个分支并合并、用断点看一个变量的值。做不完就砍小，不要延长。

### 3. 读一小节文档（3 分钟）

读你刚用过的那条命令的 man 页，或者官方文档里对应的那一节。手刚动过，这时候读文档最容易读进去，也最容易记住边界情况。

### 4. 记一行（2 分钟）

写下「今天练了什么、卡在哪、明天第一步」。三行就够。一周后回看，你会发现卡住的地方在重复，那就是下一个要专门练的点。

## 项目驱动：先有一个想做出来的东西

跟着教程敲，你永远走在别人铺好的路上；有具体目标时，卡住的地方才是你真正要学的。判断标准很朴素：**这个东西能给别人用吗**。能跑在自己机器上不算，能让别人打开一个网址用上才算。

项目别选大的。一个人两周做不完的项目，通常会停在「目录搭好了，写了两天」。选一个能在一周内出可运行版本、之后再慢慢加功能的东西，先让它能用，再让它好用。

## 三个练手项目，难度递增

| 项目 | 会用到 | 做完的标志 |
| --- | --- | --- |
| 个人书签页 | HTML/CSS、Git、静态部署 | 有一个公开网址，能增删书签，改动有提交历史 |
| 命令行小工具 | 终端、文件读写、包管理 | 能通过 npm 或 pip 装上，--help 能说清用法 |
| 带数据库的待办 | 后端、数据库、环境变量、部署 | 线上能注册登录，服务重启后数据还在 |

## 查文档的顺序：man、--help、官方文档、搜索

顺序别反。先 `man 命令` 看本地这一版的确切参数，再 `命令 --help` 看常用示例，然后去官方文档读概念章节，最后才搜索。前三个是程序自带的说明，和你手上的版本完全对得上；搜索结果是别人环境的二手信息。

搜索时把报错去噪：删掉用户名、绝对路径、版本号、时间戳，只留通用部分，再加上技术栈关键词。加 `site:github.com/issues` 能直接看到别人报过的同一个 bug，顺手看一眼答案的日期。

## 三个查用法的地方

```bash
$ man git-rebase
$ git rebase --help
$ tldr git rebase
GIT-REBASE(1)                       Git Manual                      GIT-REBASE(1)

NAME
       git-rebase - Reapply commits on top of another base tip

SYNOPSIS
       git rebase [-i | --interactive] [options] [--exec cmd]
```

> man 页里按 / 输入关键词搜索，n 跳到下一个匹配，q 退出。--help 一般打开同一个 man 页或网页版文档。tldr 是社区维护的「只给常用例子」的版本，要单独安装：brew install tldr 或 npm install -g tldr。

## 查文档时的常用键

| 操作 | macOS | Windows |
| --- | --- | --- |
| 页内搜索 | <kbd>⌘</kbd><kbd>F</kbd> | <kbd>Ctrl</kbd><kbd>F</kbd> |
| man 页里搜索 | <kbd>/</kbd> | <kbd>/</kbd> |
| 跳到页面顶部或底部 | <kbd>⌘</kbd><kbd>↑</kbd> | <kbd>Ctrl</kbd><kbd>Home</kbd> |
| 终端新开一个标签页 | <kbd>⌘</kbd><kbd>T</kbd> | <kbd>Ctrl</kbd><kbd>Shift</kbd><kbd>T</kbd> |
| 在编辑器里全局搜索 | <kbd>⌘</kbd><kbd>⇧</kbd><kbd>F</kbd> | <kbd>Ctrl</kbd><kbd>Shift</kbd><kbd>F</kbd> |

> **提示：卡住超过二十分钟，换四个动作**
>
> 先把问题写成一句话：**我想做什么、我做了什么、报了什么错、我期望什么**。写的过程经常自己就把问题解决了。
>
> 然后依次试：缩到最小复现；翻官方文档里相关那一节；搜去噪后的报错；最后才问人，问的时候把上面那句话和完整报错一起贴上。只发一句「跑不起来」，能得到的回答也只有「再试试」。

> **注意：教程地狱：收藏三十个，跑过零个**
>
> 看视频时的「懂了」是错觉，你的大脑在跟着讲者的逻辑走，不是自己在解决问题。收藏得越多，越容易产生「我在学习」的感觉，手上却什么都没留下。
>
> 解法是把教程当参考手册而不是课程表：先定一个要做的东西，卡住了再去查对应章节。还有一条：别在学新工具时同时换三个变量——新语言加新框架加新数据库一起上，报错时你分不清是谁的问题。

## 把整站串起来

回头看这一站：终端让你能指挥机器，Git 让你敢改东西，编辑器让手跟得上想法，语言让你把想法写成程序，包管理让你不必重造轮子，调试让你出错时不慌，部署让这些东西真的被别人用上。效率那一课教你怎么少敲、怎么找错，安全习惯教你别把辛苦搭起来的东西一次送掉。

接下来不用等谁来教。**挑上面三个项目里的第一个，今天晚上花二十分钟，把目录建起来、git init、写第一行。**会用工具的人不是学完所有课才开始做东西的人，是一边做一边查的人。

## 动手练一练

给自己排一周的表：每天二十分钟，写清哪天做什么，并选一个练手项目把仓库建好。

1. 选一个项目，建目录并初始化仓库 —— `mkdir my-bookmarks && cd my-bookmarks && git init`
2. 写下这一周的五个小目标，每个都要能在二十分钟内做完
3. 做第一个目标并提交 —— `git add -A && git commit -m "chore: 初始化项目"`

**完成标准**：仓库里有一条提交，纸上有五天的具体安排，两个都在就算完成。

## 小测验

<details>
<summary>展开题目与答案（3 题）</summary>

**1. 为什么每天二十分钟比周末一次五小时更容易学会？**

- A. 大脑每天只能吸收二十分钟
- B. 技能靠高频重复形成肌肉记忆，间隔复习更牢
- C. 周末的时间不属于你
- D. 长时间学习会伤眼睛

<details><summary>答案</summary>

**B**。技能靠重复与间隔巩固，每天动手会让记忆在遗忘再回忆的循环里变牢。一次长时间输入缺少动手和复习，离开教程就忘，也很难发现自己哪一步没懂。

</details>

**2. 想查一个新命令的参数，第一步应该看哪里？**

- A. 搜索前几篇博客
- B. man 命令或 命令 --help
- C. 直接去问同事
- D. 翻程序的源码

<details><summary>答案</summary>

**B**。man 和 --help 是本地这一版程序自带的说明，参数和版本完全对得上。博客与搜索结果是别人环境里的二手信息，容易过时或版本不一致。

</details>

**3. 判断一个练手项目「做完了」，最靠谱的标准是哪个？**

- A. 代码行数够多
- B. 本地能跑起来
- C. 别人能通过一个网址用上它
- D. 用到了所有学过的工具

<details><summary>答案</summary>

**C**。能部署出去被别人使用，意味着构建、环境变量、域名、日志这些真实环节都走通了。本地能跑只证明一半，代码行数和工具数量跟做没做完没有关系。

</details>
