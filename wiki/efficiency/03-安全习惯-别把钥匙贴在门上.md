# 安全习惯：别把钥匙贴在门上

> 密码、密钥、权限、备份，四件必须在出事之前做完的事

`效率与排错` · 建议 12 分钟 · 进阶

## 学完这一节，你会

- 用密码管理器做到一站一个随机密码
- 让 .env 与密钥永远进不了仓库
- 泄露之后按轮换、清历史、复查的顺序处理
- 知道 npm audit 和 3-2-1 备份怎么用

## 先想清楚谁在敲门

大多数「被盗」不是有人盯上你，而是**自动化扫描**：爬公开仓库找密钥的机器人、拿拖库（data breach）数据去撞库（credential stuffing）的脚本、扫 22 和 3389 端口的僵尸网络。它们不挑人，只看有没有把钥匙贴在门上。

习惯比工具重要，但有几件工具能把门槛拉到普通攻击之上：密码管理器、两步验证、把密钥挡在仓库外、能恢复的备份。顺序也有讲究——先做密码管理器和两步验证，收益最大；密钥和备份是下一次项目开工前该准备好的。

## 密码管理器：你只需要记住一个密码

密码管理器（password manager）把账号密码存进一个加密的库，你只需要记住一个主密码。常见的有 1Password、Bitwarden、KeePassXC；浏览器自带的保存也比「一个密码走天下」强得多。

它解决的核心问题不是「记不住」，而是**让每个站点都有独立的随机密码**。一个站被拖库，撞库脚本会拿那组账号密码去试你所有账号；一站一密，损失就停在那一个站。主密码要长、不复用、不写进任何文档，最好是一句只有你知道的短语，再加两个数字和符号。

## 两步验证：第二把钥匙单独放

两步验证（two-factor authentication，2FA）是在密码之外再要一个动态码。优先级从高到低：**硬件密钥（security key，如 YubiKey）→ 认证器 App 的 TOTP 动态码 → 短信验证码**。短信能被拦截和补卡，当兜底用，别当首选。

开启 2FA 时网站会给你一组恢复码（recovery codes），那是唯一的后路：手机丢了、App 卸载了，靠它进账号。打印出来或存进密码管理器的安全笔记，别只存在那部手机上。先开这四个：邮箱、GitHub、云服务商、域名注册商——域名丢了，站点就是别人的。

## .gitignore 示例：把钥匙挡在仓库外

```text
# .gitignore —— 放在仓库根目录

# 1. 环境变量与密钥
.env
.env.local
.env.*.local
*.pem
*.key
id_rsa
id_ed25519

# 2. 但示例文件必须提交，让同事知道要配哪些键
!.env.example

# 3. 依赖与构建产物
node_modules/
dist/
.next/
coverage/

# 4. 系统与编辑器杂物
.DS_Store
Thumbs.db
*.log
```

> 注意第 2 条：.env.example 里只写键名和注释，不写真实值。提交它，团队才知道要配哪些变量；少了这条，别人拿到仓库只能靠猜。.gitignore 对已经被跟踪的文件无效，这一点后面还会踩到。

## 先查一遍：密钥有没有已经进过仓库

```bash
$ git ls-files | grep -E "\.env|\.pem|id_rsa"
$ git log --all --oneline -- .env
.env.local
a1b2c3d fix: 加上本地配置
```

> git ls-files 列出被跟踪的文件，出现在这里就说明已经提交过；git log --all -- .env 会翻遍所有分支的历史。只删工作区的文件没有用，仓库里那份仍然在，别人 clone 下来就能看到。

## 密钥已经泄露：按这个顺序处理

### 1. 第一件事是轮换，不是删除

去服务商后台重新生成 API key、改数据库密码、撤销 token，然后更新到部署环境。删掉 .env 而留着旧密钥，等于把钥匙从门上拿下来放进抽屉。

### 2. 确认这把钥匙能干什么

看密钥的权限范围：对象存储的 key 可能能读全桶数据，某个搜索服务的 key 只是花点钱。翻访问日志和账单，看有没有异常调用，再决定要不要通知同事和用户。

### 3. 清理 git 历史

用 `git filter-repo --path .env --invert-paths`（先装 git-filter-repo）或 BFG 把文件从所有提交里删掉。这一步**会重写历史**，所有提交的哈希都会变。

### 4. 强推，并让所有人重新 clone

`git push --force --all` 之后，同事本地的旧克隆里还留着旧提交，下次 push 会把密钥带回来。必须通知他们重新拉取或重新克隆；已经 fork 的仓库和 PR 里的副本，平台方不一定清得掉。

## npm audit：看清依赖里已经公开的漏洞

```bash
$ npm audit --omit=dev
$ npm audit fix
# npm audit report

axios  <1.6.2
Severity: moderate
Server-Side Request Forgery in axios
fix available via npm audit fix
1 moderate severity vulnerability

To address issues that do not require attention, run:
  npm audit fix
```

> npm audit 读的是依赖树里的已知漏洞公告（advisory）。--omit=dev 只看生产依赖，报告更接近真实风险。npm audit fix 只在小版本范围内升级；npm audit fix --force 会跨大版本，可能直接改坏项目，执行前先提交代码。

## 最小权限：给每样东西刚好够用的权限

| 对象 | 常见错误 | 该怎么做 |
| --- | --- | --- |
| 数据库账号 | 应用和人都用 root 连接 | 应用用只有增删改查权限的账号，迁移用另一个账号 |
| SSH 登录 | root 密码登录，22 端口对全网开放 | 只允许密钥登录、禁用密码，按需限制来源 IP |
| 文件权限 | chmod -R 777 求省事 | 目录 755、文件 644，只给必须写的目录写权限 |
| CI 的 token | 直接用个人全权限 token | 用仓库级的只读或只写 token，按流水线需要分配 |
| 云账号 | 所有人共用一把长期 access key | 一人一个子账号并开 MFA，能用量身角色就不用长期密钥 |

## 公共网络与代理：中间有人听得见

咖啡厅和机场的 Wi-Fi 上，同网段的人能做 ARP 欺骗（ARP spoofing）和伪造热点（evil twin），把你的流量引到他的机器。判断标准很简单：**地址栏有没有锁、域名对不对**。HTTPS 在证书正确时内容仍加密，但对方能看到你访问了哪些域名。

代理（proxy）同理：`http_proxy`、`https_proxy` 一旦指向别人的服务器，明文流量全在对方手里，返回的内容也可能被改。用自己可控的代理，别随手装来路不明的加速器。要在不信任的网络里工作，用自己搭的 VPN 或 SSH 隧道：`ssh -D 1080 用户名@服务器` 在本机开一个 socks 代理。

## 备份：3-2-1 原则与「恢复一次」

3-2-1 原则：**3 份数据、2 种介质、1 份异地**。本机一份、移动硬盘一份、云上一份，任何一份坏掉都还剩两份。异地那份专门对付火灾、偷盗、勒索软件这类会同时毁掉本机和本地硬盘的情况。

关键不是备份，是**验证恢复**。没试过恢复的备份不算备份：每季度挑一个文件，从备份里真的还原出来打开看看。工具用 restic、borg 或 Time Machine 都行，但记得加密——备份盘丢了，里面的数据不该被别人直接读走。

> **提示：密钥只从环境变量进程序**
>
> 代码里不要出现字面量的密钥：`const key = "sk-..."` 一旦提交就永远在历史里。统一走环境变量——Node 用 `process.env.API_KEY` 配合 dotenv 读 `.env`，Python 用 `os.environ`，前端构建时用平台注入的变量（注意：打进前端包的变量等于公开）。
>
> 线上不要把 .env 传上去，用平台的环境变量面板或密钥管理服务。同一份代码在本地和线上都能跑，而密钥只存在于运行环境里。

> **注意：删掉 .env 不等于事情结束**
>
> 最常见的错误处理：发现泄露 → 往 .gitignore 加一行 → 提交 → 以为搞定。密钥仍然在历史提交里，任何人 clone 下来 `git log -p` 就能看到，扫描机器人几分钟内就能用掉它。
>
> 第二个错误：只清理了当前分支。远端分支、标签、fork、PR 副本都要单独确认。所以顺序永远是**先轮换密钥，再清理历史**——清理失败也不至于失守。

## 动手练一练

在你自己的一个真实仓库里补上 .gitignore，然后用 git 查一遍历史，看有没有 .env 或私钥文件进去过。

1. 列出被跟踪的文件，找有没有 .env 或私钥 —— `git ls-files | grep -E "\.env|\.pem|id_rsa"`
2. 翻历史，看 .env 有没有出现在某次提交里 —— `git log --all --oneline -- .env`
3. 把 .env、*.pem 写进 .gitignore 并提交这次改动 —— `git add .gitignore && git commit -m "chore: 忽略密钥文件"`

**完成标准**：两条查询都没有输出，且 .gitignore 里已经包含 .env，这一课就做完了。

## 小测验

<details>
<summary>展开题目与答案（3 题）</summary>

**1. .env 已经被提交过，这时把它写进 .gitignore 会发生什么？**

- A. 文件自动从历史里消失
- B. 不再跟踪新改动，但历史里仍有旧内容
- C. 会阻止其他人 clone 仓库
- D. 需要先手工删掉本地文件

<details><summary>答案</summary>

**B**。.gitignore 只影响还没被跟踪的文件。已提交的文件会继续被 git 管理，历史里每一次提交都保留着当时的密钥，必须重写历史才清得掉。

</details>

**2. 发现线上用的 API key 泄露，第一步该做什么？**

- A. 从最新提交里删掉那行代码
- B. 去服务商后台轮换密钥让它作废
- C. 把仓库改成私有仓库
- D. 先通知所有同事

<details><summary>答案</summary>

**B**。改私有或删代码都不能让已经流出的密钥失效，扫描机器人可能在几分钟内就用掉它。先轮换让旧密钥作废，后面的清理和通知才有意义。

</details>

**3. 3-2-1 备份原则里的那个 1 指什么？**

- A. 每天备份一次
- B. 至少一份放在异地
- C. 只保留一份备份
- D. 每年检查一次

<details><summary>答案</summary>

**B**。三份数据、两种介质、一份异地。异地那份用来对付火灾、偷盗、勒索软件这类会同时毁掉本机和本地硬盘的情况，它本身还应该是加密的。

</details>
