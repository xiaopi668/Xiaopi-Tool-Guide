# 报错排查手册

> 把「跑不起来」拆成四个固定动作，照着做就能定位到那一行

`效率与排错` · 建议 16 分钟 · 基础

## 学完这一节，你会

- 用四步法把一团报错缩小到一个原因
- 认出九种最常见的报错并知道往哪查
- 分清是命令没装、权限不够还是程序自己崩了
- 搜报错时知道该删掉哪些噪声

## 排错四步法：顺序不要跳

### 1. 读完整错误，别只看最后一行

先判断属于哪一类：**命令打不到**（command not found）、**权限或路径不对**（permission denied、no such file）、**程序自己崩了**（stack trace、traceback）、**外部依赖不配合**（端口被占、CORS、版本冲突）。类别不同，往下钻的方向完全不同。

### 2. 定位到第一处，别修最后一个症状

一次构建能滚出三百行，真正的错误通常只有一行，后面全是连带错误（cascading error）。从下往上找第一个出现 `error` 的位置，或者直接搜索 `error:` 的第一次出现。修第一个，不要修最后一个。

### 3. 最小复现，让问题稳定出现

新建一个空目录，只装那一个包、只留五行代码，把它复现出来。能稳定复现，你才有一条验证「修好了没有」的路；复现不出来就动手改，改完也不知道是自己修对了还是巧合。

### 4. 带着错误原文搜索

复制之前先做减法：删掉路径里的用户名、版本号、时间戳、临时目录名，只留通用部分，再加技术栈关键词。比如 `ENOENT .env.local vite`。错误码优先搜官方文档，加 `site:github.com/issues` 能直接看到别人报过的同一个 bug。

## 九种高频报错速查

| 报错原文 | 常见原因 | 解决 |
| --- | --- | --- |
| zsh: command not found: xxx | 没装、没进 PATH，或装在另一个 shell 的配置里 | type -a 名字 看有没有；echo $PATH 看路径；装完重开终端 |
| Permission denied | 文件没有执行位，或当前用户对该目录没有写权限 | chmod +x 脚本；写权限问题换目录或改所有者，别习惯性 sudo |
| EADDRINUSE: address already in use :::3000 | 端口被占，多半是上一次的服务没关干净 | lsof -nP -iTCP:3000 -sTCP:LISTEN 找 PID，kill -15；或换端口 |
| Cannot find module ./utils/date | 依赖没装、名字写错，或路径大小写不对 | 带点的是自己的文件，查路径与大小写；不带点的是包，npm install |
| npm ERR! code ERESOLVE | 两个包的 peer 依赖版本要求互相冲突 | npm ls 包名 看谁在要求；升降版本对齐，别长期靠 --legacy-peer-deps |
| ! [rejected] main -> main (fetch first) | 远程有你本地没有的提交，推送会被拒 | git pull --rebase origin main 再 push；共享分支不要强推 |
| blocked by CORS policy | 浏览器跨源，服务端没回 Access-Control-Allow-Origin | 服务端加响应头，或开发时用代理；curl 能通就是浏览器策略 |
| EACCES: permission denied, mkdir /usr/local/lib | 全局安装目录属于 root，当前用户写不进去 | 给 npm 换自己的 prefix，或改用 nvm；不要形成 sudo 习惯 |
| 中文变成 ??? 或 锟斤拷 | 文件按 GBK 存、按 UTF-8 读，或反过来 | file -I 看真实编码，iconv 转成 UTF-8；编辑器统一存 UTF-8 |

## command not found：先分清没装还是没进 PATH

```bash
$ yarn -v
$ type -a yarn
$ echo $PATH
zsh: command not found: yarn
yarn: aliased to echo 'use pnpm instead'
/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin:/usr/sbin:/sbin
```

> type -a 会列出所有同名命令，包括别名和函数：有时候不是没装，而是被一个别名挡住了。echo $PATH 用冒号分隔，顺序就是查找顺序，前一个目录里的同名程序会赢。装了 node 却找不到 npm 时，先怀疑版本管理器（nvm、fnm、volta）没在当前窗口初始化。

## 端口被占用：EADDRINUSE

```bash
$ node server.js
node:events:497
      throw er; // Unhandled 'error' event
      ^

Error: listen EADDRINUSE: address already in use :::3000
    at Server.setupListenHandle [as _listen2] (node:net:1740:16)
    at listenInCluster (node:net:1798:12)
    at Server.listen (node:net:1881:7)
    at Module._compile (node:internal/modules/cjs/loader:1546:14)
  errno: -48,
  code: EADDRINUSE,
  syscall: listen,
  address: ::,
  port: 3000

Node.js v20.11.1
```

> 下一步是找占用者：lsof -nP -iTCP:3000 -sTCP:LISTEN 给出 PID，kill -15 PID 是请它自己退出，能保存数据、能关连接；kill -9 是直接杀，进程来不及清理，可能留下半写状态和临时文件。Windows 用 netstat -ano | findstr :3000 拿 PID，再 taskkill /PID 12345 /F。

## Cannot find module：带点和带点的是两件事

```bash
$ node index.js
node:internal/modules/cjs/loader:1147
  throw err;
  ^

Error: Cannot find module './utils/date'
Require stack:
- /Users/you/app/index.js
    at Module._resolveFilename (node:internal/modules/cjs/loader:1144:15)
  code: 'MODULE_NOT_FOUND',
  requireStack: [ '/Users/you/app/index.js' ]
```

> 带 ./ 或 ../ 的是你自己的文件，带裸名字的（express、lodash）是 npm 包，两条修法完全不同。自己文件最常见三个原因：漏了扩展名、文件名大小写不一致（macOS 默认不区分大小写，Linux 服务器区分，本地能跑上线就崩）、文件其实在上一层目录。ESM 项目里必须写全 .js 后缀，否则报 ERR_MODULE_NOT_FOUND。

## npm ERR! ERESOLVE：依赖树打架

```bash
$ npm install react-dom@18
npm ERR! code ERESOLVE
npm ERR! ERESOLVE unable to resolve dependency tree
npm ERR!
npm ERR! While resolving: app@0.1.0
npm ERR! Found: react@17.0.2
npm ERR! node_modules/react
npm ERR!   react"^17.0.2" from the root project
npm ERR!
npm ERR! Could not resolve dependency:
npm ERR! peer react"^18.2.0" from react-dom@18.3.1
npm ERR! node_modules/react-dom
npm ERR!   react-dom"18" from the root project
```

> 这几段把因果写得很清楚：项目里装的是 react 17，react-dom 18 要求 peer 是 18。npm ls react 能看到谁把它锁在 17。--legacy-peer-deps 能让安装过去，但装出来的是 npm 认为不成立的依赖树，之后运行时报的错离真正原因更远。

## git push 被拒：(fetch first)

```bash
$ git push origin main
To github.com:you/app.git
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'github.com:you/app.git'
hint: Updates were rejected because the remote contains work that you do
hint: not have locally. This is usually caused by another repository pushing
hint: to the same ref. You may want to first integrate the remote changes
hint: (e.g., 'git pull ...') before pushing again.
```

> 照 hint 做，但要选对合并方式：git pull --rebase origin main 把你本地的提交接在远程之后，历史是一条直线；直接 git pull 会多出一个合并提交。git push --force 会覆盖远程，别人的提交直接消失——共享分支上不要用；非用不可时用 --force-with-lease，它在远程被人改动后会拒绝推送。

## Permission denied 分两种，解法相反

看报错里的路径，先分清是**执行**还是**写入**。跑自己的脚本报 `zsh: permission denied: ./deploy.sh`，是文件没有执行位，`chmod +x deploy.sh` 立刻解决。给 chmod 加 `-R 777` 会让目录里所有文件对所有人可读可写可执行，事后没人能查清是谁改的，别拿它求省事。

写系统目录报 `EACCES: permission denied, open /usr/local/lib/node_modules`，说明全局目录属于 root。正确做法是给 npm 换一个自己的前缀（`npm config set prefix ~/.npm-global`），而不是凡事 sudo——用 sudo 装出来的文件，以后每次升级都要 sudo。

## CORS 不是服务器拒绝了你

控制台原文：`Access to fetch at http://localhost:5173/api from origin ... has been blocked by CORS policy: No Access-Control-Allow-Origin header is present on the requested resource`。这是**浏览器**的策略（同源策略与 CORS），服务器其实回了数据。

最直接的证据：用 `curl` 请求同一个地址能拿到 JSON，说明接口本身是通的。两条正路——服务端加 `Access-Control-Allow-Origin` 响应头（带 Cookie 时还要 `Allow-Credentials`，且不能用通配符），或者开发时用代理把请求变成同源（Vite 的 `server.proxy`）。关掉浏览器安全检查只是把问题藏起来，上线照样炸。

## 乱码：先确认文件到底是什么编码

症状：本该显示中文的地方出现 `锟斤拷`、`????`、`Ã¤Â¸Â­`，或者 JSON 第一行解析失败但肉眼看不出问题（那是 BOM，文件开头三个看不见的字节）。

先查真相：macOS 用 `file -I 文件名`，Linux 用 `file -i 文件名`，输出里的 `charset=utf-8` 才是结论，别靠编辑器猜。GBK 存的文件按 UTF-8 读就是乱码的根源，`iconv -f GBK -t UTF-8 old.txt &gt; new.txt` 转换，原文件留着比对。Windows 的 cmd 默认代码页常是 GBK，用 `chcp 65001` 切到 UTF-8 能解决终端里的显示问题。

> **提示：搜报错前先做减法**
>
> 原样复制 `Error: ENOENT: no such file or directory, open /Users/xiaopi/app/.env.local` 去搜，命中的是别人机器上的路径，几乎没有结果。删掉用户名、绝对路径、版本号、时间戳，留下 `ENOENT .env.local vite`，命中率立刻不一样。
>
> 再加技术栈和场景词，比如 `docker compose`、`next build`。看答案先看日期和版本：三年前的解法在新版本上经常失效，尤其是构建工具和 Node 相关的报错。

> **注意：四个会把小问题放大成大问题的动作**
>
> **sudo 一切**：sudo 只是跳过权限检查，产生的 root 文件和「以后次次 sudo」会陪着你。
>
> **报错先 rm -rf node_modules**：依赖冲突多半是版本问题，重装只解决一半，还损失了现场。
>
> **直接 kill -9**：进程来不及释放端口和临时文件，有时让「端口被占用」更严重。先 -15，等两秒还没退再 -9。
>
> **把 --force 当解法**：`git push --force` 会盖掉别人的提交，`npm audit fix --force` 会跨大版本升级依赖，两者都能把能跑的东西修成跑不起来的。

## 动手练一练

故意造一个「端口被占用」，然后用 lsof 找出占用者并正确结束它，把四步法完整走一遍。

1. 在一个窗口起一个占住 8000 端口的服务 —— `python3 -m http.server 8000`
2. 在另一个窗口起同一个端口，读完整个报错 —— `python3 -m http.server 8000`
3. 找出占用 8000 的进程号 —— `lsof -nP -iTCP:8000 -sTCP:LISTEN`
4. 用 kill -15 结束它，再确认端口空出来了 —— `kill -15 进程号`

**完成标准**：能说出占用端口的进程是谁、为什么 -15 比 -9 更安全，这课就到位了。

## 小测验

<details>
<summary>展开题目与答案（3 题）</summary>

**1. 一次构建滚出三百行报错，你应该从哪里读起？**

- A. 最后一行的最后一个词
- B. 最上面第一处 error，再往下看连带错误
- C. 中间的任意一行
- D. 清空日志重新跑一次

<details><summary>答案</summary>

**B**。构建和运行时报错大多是连锁的，第一处才是根因，后面的多半是被它带出来的次生错误。从第一条 error 开始，能省掉一路追症状的时间。

</details>

**2. lsof -nP -iTCP:3000 -sTCP:LISTEN 里的 -nP 有什么用？**

- A. 只显示 node 进程
- B. 不解析主机名和端口名，直接显示数字
- C. 强制结束占用端口的进程
- D. 列出所有 TCP 连接

<details><summary>答案</summary>

**B**。n 禁止把 IP 反查成域名，P 禁止把端口 3000 翻成服务名。两个都关掉，输出更干净也更快，端口号一定以数字出现，方便你直接抄进下一条命令。

</details>

**3. npm 报 ERESOLVE，加上 --legacy-peer-deps 装上了，代价是什么？**

- A. 依赖体积变大
- B. 跳过 peer 依赖检查，装出的依赖树可能互不兼容
- C. 项目不能再提交到 git
- D. 以后不能再执行 npm install

<details><summary>答案</summary>

**B**。这个参数让 npm 忽略 peer 冲突继续安装，装是装上了，运行时仍可能因为版本不匹配崩掉，而且报错位置离真正原因更远。先对齐版本才是解法。

</details>
